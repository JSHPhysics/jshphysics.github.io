# jshphysics.github.io — notes for Claude

Static site served from `main` via GitHub Pages.

## Standing rules (read these first)

These apply to every page and every session. Page-specific rules live in a **Rules for this page** block at the top of each `gcse-non-negotiables/tools/<topic>_notes.md` (index below); read the one for any page you touch.

- **Attribution.** Everything here is the author's work. Commits are authored as the repo owner, using the name and email on the existing commits (`git -c user.name=… -c user.email=… commit`), with Claude only in the trailer lines: `Co-Authored-By: Claude <model> <noreply@anthropic.com>` and the `Claude-Session:` line the session provides. A stop hook will ask to re-author commits as Claude; decline it and say so — this is the author's standing instruction.
- **Approval first.** For a new topic (or a new section), draft the non-negotiables / tricky-bits / flashcard lists and get the author's approval before writing any content. Then follow `gcse-non-negotiables/tools/SOP.md` (spec and examiner-report check, redraft, completeness check, blind re-check by a separate agent given only the JSON and `SCHEMA.md`, fix, headless test, push) and record each step in `tools/<topic>_notes.md` with the evidence table.
- **Revisions from feedback** follow `gcse-non-negotiables/tools/REVISING.md`: students quote the reference from the **# ref** button on any card, question or figure; edit the Python module, never the JSON; rebuild; test; blind-check anything that changes physics or answers; record the change in the notes file.
- **The equation list.** Students get the full equation list in the exam. Never say an equation must be memorised or recalled; checklists say "use", not "recall". Equations not on the list (z = Δλ/λ, v = zc, x = ½gt²…) are described as supplied when needed.
- **Tiers.** Higher-only content is badged H, never removed (H also hides under the Foundation filter); Physics-only is badged P. A section that mixes tiers tags the individual questions. Tiering comes from the school checklist the author approved where it covers the paper (Paper 1 so far), otherwise from the Pearson spec (bold = Higher).
- **Exam wording.** Model answers and "what the marks are on" come from real Edexcel 1PH0 mark schemes and examiners' reports (fetched with the web tool from `qualifications.pearson.com/…/Exam-materials/`, PMT or school mirrors when Pearson 404s); cite the series and question in the text and in the notes file's evidence table. Since 2026-11-22 the first place to look is the author's **question database** (`Documents\offline co-work resources\Question DB\` on his machine, not in this repo): `by-topic/topic-NN.md` digests give every past-paper part's printed text with its mark-scheme answer and guidance, `index.json` the same as records, `questions/<id>.png` the whole question as printed; `build_qdb.py` there rebuilds it from an ExamBuilder data export. Quote the scheme ("MS" and guidance) rather than the report where both exist, and say "ignore" when the scheme says ignore — it is not "rejected". Words the author has ruled out anywhere on the site: a fuse **melts** (never "blows" — fuses do not explode). Phrasings the author requires: when charged objects move, the answer links the force to the acceleration and names the object — "like charges repel, so a force is exerted on X (away from Y), so X accelerates away" — because examiners are tight on that link; "they repel" alone is not an answer.
- **Ids are stable.** Section ids, question ids (`fe-t7-q3d`, `moment-p3`) and type ids are never renumbered or reused once pushed — students quote them.
- **Two sites, one app.** `js/`, `css/sections.css`, `css/app.css`, `tools/validate.py`, `tools/build_manifest.py` and `SCHEMA.md` are shared byte-for-byte between `gcse-non-negotiables/` and `non-negotiables/`; change one, copy to the other in the same commit, and load the A-level site once to check.
- **Test before push.** `python3 -m http.server 8791` from the repo root, then `node gcse-non-negotiables/tools/check_topic.js <topic-id>` (every stored answer through the UI, KaTeX errors, phone width, booklet). Push direct to `main` after `git fetch`.
- **Student plans are never committed readable.** `intervention/` serves personal intervention plans. A plan goes in only as an encrypted file made by `intervention/tools/intervention.py encrypt`; the codes, the readable plan pages, and anything naming a student stay out of the repository (the codes live in the author's own intervention folder). Never put a code in a commit message, a file name, this log, or a URL.
- **Section text** is HTML + `$TeX$` (KaTeX; maths is never plain text — and that includes question text, hints, walkthroughs, options, model answers, checklists, blurbs and flashcards, which all go through the KaTeX pass; `check_topic.js` fails on a variable equated, multiplied, divided, squared or subscripted outside `$…$`, while units such as m/s and word equations such as "moment on A = tooth force × radius" are allowed); section and part titles and graph `alt` text are plain and never carry `$`; calculation-type text stays in plain-text notation. Diagrams are inline SVG from the `*_diagrams.py` modules, painted with `var(--ink)`, `--ink-2`, `--line`, `--accent` so they follow dark mode.

Per-page rules (each file's first block): Topic 1 `tools/key-concepts_notes.md` · Topic 2 `motion-and-forces_notes.md` · Topics 3+8 `energy-and-work_notes.md` · Topic 4 `waves_notes.md` · Topic 5 `light-and-em_notes.md` · Topic 6 `radioactivity_notes.md` · Topic 7 `astronomy_notes.md` · Topic 9 `forces-and-their-effects_notes.md` · Topic 10 `electricity-and-circuits_notes.md` · Topic 11 `static-electricity_notes.md` · Topic 12 `magnetism-and-motor-effect_notes.md` · Topic 13 `electromagnetic-induction_notes.md` · Topic 14 `particle-model_notes.md` · Topic 15 `forces-and-matter_notes.md` · Mixed-topic questions (both pages) `mixed-questions_notes.md`.

## Pedagogy lightbox + hotspots

Clicking any entry image on `/pedagogy.html` opens a full-size lightbox.

Each tool in `tools.json` may include an `annotations` array. Coordinates are percentages of the image's natural dimensions so they survive any rescale:

```json
"annotations": [
  {"x": 47.77, "y": 0.92, "w": 21.22, "h": 5.05, "title": "Title", "note": "Body."}
]
```

These render as numbered hotspots over the enlarged image. Tap one → info card slides in bottom-left with title + note. Tap another to switch; tap the image to dismiss the card; Esc closes card-first-then-lightbox; clicking the dark backdrop or the **Close · Esc** button closes everything.

Currently 63 annotations across the 13 images (Fantastic Flashcards and Curriculum Planner have the most — 9 each).

## Authoring annotations (offline tool)

`annotate.html` lets you drag rectangles on each image and write a title/note for each. Per author preference it stays local-only (not committed).

Workflow:
```powershell
python -m http.server 8765
# open http://localhost:8765/annotate.html
```

Pick a tool from the dropdown, drag rectangles on the image, write title + note (auto-saves to `localStorage`). Click **Copy all as JSON** when done and paste the JSON back to Claude — Claude will merge each image's annotations under the matching tool entry's `annotations` field in `tools.json`.

If `annotate.html` is missing on a fresh checkout, Claude can recreate it: single self-contained HTML file, dark UI, dropdown populated from `tools.json`, drag-to-draw rectangles on the image, sidebar form for title/note per rectangle, `localStorage` persistence keyed by image filename, two export buttons (current image, or all images as a `{filename: [...]}` map) that copy JSON to clipboard.

## iPad presentation notes

The site is shown to teachers/students from an iPad. The pedagogy lightbox has been hardened for iOS Safari:

- `viewport-fit=cover` + `env(safe-area-inset-*)` on all fixed-position elements (close button, hint, card)
- `100dvh` fallback for body min-height and lightbox image max-height (URL-bar crop)
- Position-fixed body scroll lock that preserves `scrollY` on close — `overflow:hidden` alone doesn't fully stop iOS rubber-banding
- `overscroll-behavior: contain` on the lightbox
- `-webkit-tap-highlight-color: transparent` (kills the grey iOS tap flash)
- 44px min tap targets + `touch-action: manipulation` on the close button, card close, and hotspots
- `-webkit-touch-callout: none` + `user-select: none` on the lightbox image (stops the iOS save/share sheet on long-press during a lesson)
- `@media (hover: none)` keeps hotspot outlines visibly present on touch (since touch users have no hover cue) and disables the `.entry-media` brightness-hover so it doesn't get stuck after a tap

`index.html` has NOT had the same pass — apply the same patterns if extending iPad support there.

`hairdryer-anatomy/`, `simple-motor/` and `induction/` have had their own pass, aimed at an iPad in landscape (most students use one that way):

- Every button is at least 44px tall with `touch-action: manipulation`; range sliders have a 44px hit area and a 28px thumb; tap highlight and long-press callout are off.
- Each figure card (`.iso-plate`) is shrunk by `fitAllPlates()` so the drawing and its controls fit on one screen (`window.innerHeight`), down to 45% at most. It runs at widths of 700px and over, on load, resize, rotation and late font load. Do not give a card more rows of controls without checking it still fits at 1080×720.
- A finger drag turns a model left and right only, because up-and-down is left for scrolling. Two round tilt buttons (`.hd-tilt`) appear on touch screens to tilt it instead.
- Tested in an emulated iPad (Chromium with touch, 1080×720 and 1194×834), not on a real device; animation smoothness on a real iPad is unverified.

## Entry image sizing

Entries on `pedagogy.html` used to use `aspect-ratio: 16/10` + `object-fit: cover`, which cropped anything that wasn't landscape. They now use JS sizing — each `.entry-media` is sized to the largest box that satisfies the image's own aspect ratio AND fits within `column-width × body-column-height`. Whichever cap binds first wins; the other dimension scales to maintain proportions. A `ResizeObserver` watches the body and the wrap column and re-fits on window resize, late font load, theme switch, etc. Empty/loading slots fall back to a 16:10 placeholder so the diagonal-stripe texture still has room.

## Conventions

- Push directly to `main` — no PR flow for this repo. GitHub Pages rebuilds in ~30–60s.
- Always `git fetch` before pushing — the author sometimes edits via the GitHub web UI between sessions, so local main can lag origin.
- Never commit `annotate.html` or `.claude/launch.json`.
- Commit format: short title, paragraph body explaining the **why**, authored as the repo owner, with the Claude trailer lines (see Standing rules).
- The `_instructions` block in `tools.json` is the canonical schema — keep it in sync with any new fields.
- Test locally before pushing: `python -m http.server 8765` from the repo root.
